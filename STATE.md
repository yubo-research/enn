## Tried and rejected
- File fragmentation (0230), writeback contention (0229), 8K alignment (0229 data) as causes of slow buffer-file reads.
- Smaller fence granularity (16 vs 64 rows): only -10% query (0228).
- Fixed number of disk levels with RAM upper buffers: query unchanged, RAM grows with N (0227).
- Run-indexed buffers: queries 3.8x slower than full scan (0223). Per-child buffer segments: adds 5-10x slower (0221).
- Moving leaf metadata into the code page; one page per leaf (0219). Keeping the upper tree in memory (0173). Dropping the prefetch (0215).
- Leaf coefficient c=3: recall 0.79 at D=10 (0217).
- Wider AVX2 loop in l2_sq_f32 for D<32 (0233): no gain (1.87 vs 1.66 us/row insert).
- Morph work as the cause of the in-RAM add gap (0232).
- Leaf-id tail on the 2nd page of a 2-page code region (D=100): adds +8% in RAM (p=0.002), +25% cold at N<=30 (0236). Leaf test by depth (assumes balanced tree): 6635 vs 2708 pages at D=10 N=3e5, cause unproven; replaced by explicit parent bits (0236).
- 4-bit raw-coordinate codes as default (0237): mid-N cold loss on structured data, slower in RAM. Kept behind ENN_CODE4=1 (off). Even with refine-more, raw 4-bit loses 1.23-1.46x at 3e3-3e4 (5-dim; 0238).
- Residual codes re-encoded from decoded rows on split/morph (0238 v1): stored bounds accumulate (median 2.2x fresh, p90 5.5x); no cold gain over raw 4-bit.
- Residual codes as default (0238): adds 2.9x slower in RAM; kept behind ENN_CODE4=2 (off).
- Lazy re-anchoring and anchor inheritance for residual codes (0239): every setting trades add cost against slack/query cost; none beats 8-bit on both at every N. Deferring morph's exact re-reads until a move is chosen: no add change (kept; no effect on results).
- Tight certification boundary min(last, min_excluded(r_i - e_i)) (0237): no fewer retries; removed. Larger coded pool (CODE_EXTRA 100/300) does not raise 4-bit recall (0237).
- One-page (64-row) per-node add buffers, at every level or at leaf parents only (0240): cliff no later, post-cliff adds 1.4-1.6x slower, in-RAM adds up to 1.6x slower. Reverted; patch kept.
- Residual 4-bit codes with exact train_x re-reads as a cliff fix (0241): cliff 3.3x earlier. Shrinking code bytes as a cliff fix (0241): only rescales the onset (1.5x for half the code bytes).
- Replaying buffered rows from the root (0242): rows scatter over ~430 leaves per 1000-row flush; cliff only 1.6x later. Kept as diagnostic ENN_PBUF_ROOT=1.
- Staggered buffer capacities R*(0.5..1) (0243; ENN_PBUF_STAGGER=1, off): with buffers at every level there are no flush waves to break; 256M band means 53/74/102 vs 64/70/76 unstaggered (1 run each). Kept as a flag.
- R=300 with every-level buffers (0243): adds 1.7-2.2x worse past the cap (166 vs 76 us/row at 7e6-1e7; 1460 vs 850 B/row read), though in-RAM queries 1.6-1.75x vs 2.6-2.7x at R=1000.

## Operator ruling on design method (2026-11-15)
- The cliff at the cap is not a property of the problem. It comes from treating memory as the store: letting the page cache hold everything until it is full is not an algorithm, and shows no understanding of how the data is used. Stop treating "a step of cold-read size is paid by any disk design" (0224, 0225, 0231) as settled; that conclusion rests on a RAM-until-full design.
- Design order: (1) the best on-disk algorithm you can build, O(lnN) and fast, judged by its true on-disk cost from N=1 (below the cap, today's "disk reads" are really cache hits; 0225: 1.7 vs ~200 us). (2) Then use memory as a cache, choosing what to keep from measured access patterns: what every operation touches, and what the workload touches often. A cache chosen this way degrades gradually as N grows (contributing to the lnN slope), not all at once at the cap.
- Quality target is statistical parity with main (error bars, tests), not exactness; approximations are allowed.
- Beating main at small N is an engineering goal, not a conflict with the above.

## Operator ruling on priorities (2026-11-15, after 0240)
- Priority: a+b lnN scaling of both add and query, from N=1 through data >=10x the cap, comes before beating main on in-RAM wall time. Do not reject a change for being slower than main in RAM if it is what makes the curves lnN; record the in-RAM cost and move on. (Answers the add-parity question from 0226 and the slower-add question from 0238.)
- A constant-factor increase in query cost is acceptable in exchange for lnN adds, provided queries stay a+b lnN and quality stays at statistical parity. (Answers the 0240 question; size the constant by measurement, don't wait for a number from the operator.)
- 0240 does not refute per-level buffering: it used 64-row buffers, while ideas.md P1 and 0200 say buffers must be much larger than a page (~1000 rows). Test buffering at the size the theory requires (buffer tree, Arge 2003; Be-tree, Bender et al. 2015) before concluding anything.
- Queries are already a+b lnN in true on-disk cost (0235-0238). The open work is (a) lnN adds across the cap and (b) step 2 of the design method: a cache chosen from measured access patterns.
